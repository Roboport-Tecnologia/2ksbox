## What kind of box this is

A Windows 11 box keeps the launcher, the bundle format, snapshots, the
player window and the in-process QEMU. It uses none of the era work: no
`d3dpt-vga` (Windows 8 and later refuse XP-model display drivers), no
Voodoo 2, no x87 or SSE fast paths, no guest-tools ISO. Its display is
Microsoft's Basic Display Adapter on a plain framebuffer, with no 3D,
which is enough for office work.

## What Windows 11 checks

| Check | Where | What we give it |
|---|---|---|
| UEFI | setup, hard | EDK2 (below) |
| Secure Boot capable | setup | EDK2's secure build. Off is enough to install |
| TPM 2.0 | setup, BitLocker, Hello, some company policies | libtpms in QEMU (below) |
| 4 GB RAM, 64 GB disk, 2 cores | setup | the family's defaults |
| CPU on Microsoft's list | setup only | a current CPU model under KVM/WHPX/HVF. Under TCG, the `LabConfig` `BypassCPUCheck` key during setup |
| SSE4.2 and POPCNT | 24H2 and later, hard (the kernel uses them) | TCG has both, as does any host CPU of the last ten years |

Setup can also skip the TPM check (`BypassTPMCheck`). We don't rely on
that. The user wants this for work, and BitLocker device encryption,
Windows Hello and company compliance policies need a real TPM.

## The Mac: Windows on Arm under HVF

On Apple Silicon an x86 guest runs under TCG. Win98 and XP are fine
there because their software expects a 500 MHz machine. Windows 11
expects a current multi-core x86 and runs Defender, indexing and updates
in the background. I expect x86_64 Windows 11 under TCG on the Air to
boot in minutes and stutter at the desktop. Step 1 measures it.

UTM, Parallels and VMware Fusion all run **Windows 11 on Arm** (ARM64) as
the guest, under Hypervisor.framework at close to native speed. Microsoft
publishes the ARM64 ISO. Its own x64 emulation (Prism) runs most x64
programs, and that costs less than emulating the whole machine. For us
that means:

- A third QEMU target, `aarch64-softmmu`, built on Arm hosts
  (`scripts/configure-qemu.sh`).
- The `virt` machine with `-accel hvf -cpu max` (the host's CPU under
  HVF). Our TCG patches are i386-target code and do not apply to it.
- Devices Windows ARM64 drives in the box: AHCI for the disk and CD-ROM
  (on our own EDK2, which can boot from it), `qemu-xhci` with keyboard
  and tablet, `ramfb` and `virtio-gpu-pci` for the screen, HD Audio. Networking needs
  virtio-win's ARM64 `netkvm`. Step 4's results have the rest.
- Kernel-mode drivers inside the guest (company VPN clients, endpoint
  agents) must have ARM64 builds. Prism does not run x64 drivers. Some
  companies' tools will not have them.

On Linux hosts, x86_64 Windows 11 under KVM is the box; on Windows hosts
WHPX, with no TPM until QEMU has one there (step 2), and no Secure Boot
("The launcher's machine on a Windows host" below).

## The TPM: libtpms inside QEMU

QEMU has the TPM devices: `tpm-crb` (q35), `tpm-tis` (ISA) and
`tpm-tis-device` (the ARM `virt` machine). What it lacks is a TPM to put
behind them. Its `emulator` backend talks over a socket to **swtpm**, a
separate process built on **libtpms** (IBM's TPM 2.0, derived from the
TCG reference code).

The plan is a backend that links libtpms into QEMU, `-tpmdev
libtpms,id=tpm0,state=<file>`, instead of shipping swtpm:

- One process, as ADR-002 wants. There is no sidecar to start, supervise
  and fit into the Flatpak sandbox.
- The backend calls `TPMLIB_Process()` for each command. Through
  `TPMLIB_RegisterCallbacks` it stores the TPM's permanent state in one
  file in the machine's bundle.
- Snapshots carry the volatile state (`TPMLIB_GetState` /
  `TPMLIB_SetState`) in the backend's vmstate. If the permanent state is
  lost, BitLocker asks for its recovery key, so cloning a machine copies
  the file and deleting one deletes it.
- It is C inside QEMU, which ADR-004 allows, the same pattern as
  `libsynth` behind `hw/audio`. Writing a TPM 2.0 in Rust is months of
  crypto and spec work, and nobody has written a complete one.
- **libtpms needs OpenSSL's libcrypto.** That is a new library for
  `scripts/build-deps.sh` (static, pinned; Linux and macOS, not
  Windows, which has no TPM yet: step 2).

A known limit: libtpms's endorsement key has no manufacturer certificate
chain that Microsoft trusts. Anything that attests the TPM to Microsoft
will probably fail: Autopilot self-deploying mode, device health
attestation, and the Intune compliance rules built on them. Nobody has
tested this yet. Hyper-V's own vTPM has a similar problem.

## Firmware: EDK2

Yes, Windows 11 needs UEFI. QEMU's `pc-bios/` already carries EDK2 builds
from its pinned `roms/edk2`: `edk2-x86_64-secure-code.fd`,
`edk2-aarch64-code.fd`, and the variable store templates
`edk2-i386-vars.fd` (also used by x86_64) and `edk2-arm-vars.fd`. Every
package already ships `pc-bios/`. Step 1 uses them as they are.

- x86_64 with Secure Boot: `-machine q35,smm=on`, `-global
  driver=cfi.pflash01,property=secure,value=on`, the code as a read-only
  pflash, and the machine's own copy of the vars as a writable one.
- Each machine gets its own vars file in its bundle (boot order, Secure
  Boot state), copied from the template when the machine is created.
  Snapshots include it.
- QEMU's templates have no Secure Boot keys enrolled, so Secure Boot is
  available but off. That passes setup. Turning it on needs Microsoft's
  keys in the template, enrolled at build time with virt-firmware's
  `virt-fw-vars` (Python, runs under uv). Microsoft's 2011 certificates
  expire during 2026, so enroll the 2023 ones too.

## The player and the launcher

Built in step 3 ("Step 3's results" below):

- **One player binary per target, each linking its QEMU** (doc 11). The
  era's `2ksbox-player` links i386; `2ksbox-player-x86_64` is the same
  player built with `--features qemu-x86_64` into `target/qemu-x86_64`,
  and the launcher starts the one a machine needs
  (`player::player_binary_for`). The first version had one player
  opening `libqemu-embed-<target>` at run time (`dlopen`). Reverted the
  same day (user): patch 63 reserves TCG's code buffer next to the
  helpers from a constructor that must run when the image loads, before
  `main()`, and a later `dlopen` loses that on Apple Silicon (doc 22
  §5.0). The cost is a second 23 MB player in the Linux package.
- **`launcher-core`'s `Windows 11` family** (`Family::Win11`,
  `bundle::Machine::modern_args`): a q35 with SMM, EDK2's secure build,
  the libtpms TPM on CRB, the disk on AHCI, 4 GB, up to 4 vCPUs,
  `-cpu max`, `Accel::Auto`, HD Audio, the standard VGA, the tablet on
  xHCI, an e1000e with networking, the RTC in local time. The firmware
  variables (`efi_vars`, a qcow2) and the TPM state (`tpm_state`) are
  bundle files; clone copies them.
- **The form** shows what applies (no processor, Voodoo 2, MIDI port,
  floppy or boot order) and says what the family is; the launcher
  hides the rows the model says do not apply (ADR-014).

**Our TCG patches and an x64 guest.** `target/i386` is compiled into both
system emulators, so the TCG run above used the whole queue. Patches 06,
11 and 24 have long-mode branches, and the `accel/tcg` patches do not
care about the guest's mode, but no battery or benchmark has ever run a
64-bit guest. The queue was also tuned for era code (x87, SSE1/2), while
x64 Windows is SSE2 scalar math and AVX/AVX2 (`-cpu max` offers it),
which goes through helpers we never touched. A crash under TCG on an x64
guest could be one of our patches. The control is the same boot with the
switches off (patch 29's `*-fast=off`, `QEMU_TCG_OPTS`). Making x64
Windows fast under TCG would be its own optimization project, and the
TCG number above is why the Mac gets the ARM64 guest instead.

## Step 2's results (2026-10-01)

`-tpmdev libtpms,id=tpm0,state=<file>` with `-device tpm-crb`. The
backend (`tpm/qemu/tpm_libtpms.c`, patch 75) calls `TPMLIB_Process` on
QEMU's TPM worker thread. Its storage callbacks keep libtpms's "permall"
blob in the one state file, replaced atomically; a missing file is a
TPM libtpms manufactures on first start. Snapshots carry the permanent
and volatile state, and `loadvm` writes the snapshot's permanent state
back to the file, so the TPM always matches the disk it booted with.

- `tools/tpm-qtest.py` passes all 19 checks (the `tpm-qtest` host check):
  a fresh TPM, a restart on the same file, savevm / loadvm, `info tpm`.
  No guest and no firmware: qtest is the CPU.
- Windows 11 boots on it under KVM (desktop in 18.9 to 27.1 s, clean
  power-off). Its elevated `Get-Tpm` says ready and owned, and the
  endorsement key's SHA-256 is the same on libtpms and on swtpm
  (`faa2cc0c…01b5`): the backend took over swtpm's TPM, so Windows saw
  no new chip. The spike's `TPM=libtpms` does that the first time: swtpm's
  `tpm2-00.permall` is a 10-byte header and one tag-length-value record
  (tag 1, plain) around the same blob.
- QEMU allows one `-tpmdev` of any type ("Only one TPM is allowed"),
  which matches libtpms's one global TPM.
- libtpms 0.10.2 needed one deps patch on this box's glibc 2.44
  (`patches/deps/libtpms/01-strstr-const`, from libtpms's master).
  OpenSSL is 3.5.9 (LTS), static, no programs or loadable modules.
  On Linux both are hidden in QEMU's link like GLib, so a process with
  its own OpenSSL never mixes the two.
- **Windows hosts have no TPM yet.** QEMU 9.2's meson (and 11.1.2's) refuses
  `CONFIG_TPM` on Windows ("TPM emulation only available on POSIX
  systems"), because both upstream backends need POSIX. Ours needs
  only a thread pool, so lifting that for the libtpms backend alone is
  the Windows step, with libtpms and OpenSSL in the Windows build (MSYS2).
- The Windows 11 elevated report needs a click on UAC's Yes: Windows
  11's prompt has no Alt+Y, and focus starts on No.

### The window's size (2026-10-01)

The player passes its window's drawable size, in physical pixels, and
its DPI to the console on show (embed API v9,
`qemu_embed_set_window_size`; QEMU's `dpy_set_ui_info`, which virtio-gpu

than the guest's mode.

  the Air's screen, and after a resize and a restart from inside Windows

  reboot, so the player sends every resize and the next start uses it.

  only a Microsoft-signed one loads, so it is upstream's to fix.
- The first event after a start re-plugs the monitor (viogpudo's

### Setup starts from the disc by itself (2026-10-07)

The user's first install through the launcher (the app, Arm ISO in the
drive) landed in the EFI shell. Two causes, both invisible to
`win11-spike.py`, which boots on fresh variables and sends Enter for 40 s:

- **The variables' boot order buried the disc.** The machine's first
  start had an empty drive, so the firmware recorded drivers disc
  (`QM00005`), disk, EFI shell. A disc inserted later gets a new option
  *after the shell*. Fixed with `bootindex` (`bundle.rs`): the disk 0,
  the user's drive 1, so QEMU's boot order (EDK2's `QemuBootOrderLib`)
  wins over what the variables kept. With a blank disk the firmware goes
  on to the disc; once Windows is installed the disk boots and the disc
  is never started.
- **Setup's "Press any key to boot from CD or DVD" on a black screen.**
  `cdboot.efi` waits five seconds for a key and otherwise hands back to
  the firmware. Nothing of it reaches the serial line, and on ramfb the
  user saw only black. The disc's `efi/microsoft/boot/cdboot_noprompt.efi`
  returns at once when started from the firmware's UDF view of the disc
  (it wants the El Torito image), so the prompt is answered instead: a
  Windows 11 machine's serial port is `-serial chardev:fwcon`, which the
  player supplies on a socketpair (`player-core/src/boot_prompt.rs`).
  EDK2 prints each option it starts there (`PlatformBmPrintScLib`, in
  ArmVirtQemu and OVMF, release builds too); on
  `BdsDxe: starting Boot… "UEFI QEMU DVD-ROM …"` the player writes a
  carriage return back, which EDK2's terminal driver turns into the key
  `cdboot.efi` reads. A key that arrives before `cdboot.efi` reads stays
  queued, so nothing waits, and the window need not have the keyboard.
  The player's log shows every `[firmware] BdsDxe:` line.

Checked on the Air with a copy of the user's variables: disk (not
found), the disc, the prompt answered, setup's language page 40 s after
start. `tools/win11-boot-prompt-test.sh` repeats it from a new machine.
An installed Windows (a fresh `win11-spike.py install`, `build/w11i`)
booted on the same arguments with the ISO still in the drive goes
straight to its "Windows Boot Manager" option (the disk's `bootindex`
matches its `HD(…)` path) and the desktop; the disc is never started.
x64's OVMF prints the same line but is not checked yet (Linux).

Fixed since (protocol v23, driver 0.3.10.0):
- The user-mode driver's log reached nothing: it escaped to
  `\\.\DISPLAY1`, which on Windows 11 is often Basic Display. It now
  tries each display until one takes the escape, and names the process
  at OpenAdapter (StartMenuExperienceHost, SearchHost, consent.exe,
  Explorer, DWM, OneDrive open ours).
- **Blts with a shared target were refused** unless both sides were
  render targets: DWM fills its shared targets from plain textures, reads
  them back into textures (acrylic) and into system memory
  (GetRenderTargetData). BLT (op 81) now goes both ways between a plain
  texture and a colour target (the host reads or writes the texture's
  VRAM), and a shared target into system memory goes through a lockable
  readback stage of the device's own.
- **The host's contexts leaked**: a process that ended without the
  user-mode driver's DestroyDevice left its context on the host (250
  and more). CreateContext's private data now carries the host context
  (`D3DPT_CTX_PRIV`), and the kernel driver's DestroyContext destroys it
  at the next submission. With the blits fixed the device churn stopped
  too: a handful of devices a boot, 5 to 8 host contexts.
- A render target the host drew into keeps its host pixels when WDDM
  moves its allocation (the moved VRAM copy is the older one).

Fixed since (protocol v24, driver 0.3.17.0, 2026-10-09):
- **The taskbar's icons sat on squares of wallpaper and the tray's
  background was the wallpaper.** The icons were never missing: DWM
  redraws only dirty regions, and in each it paints the wallpaper, then
  the taskbar's background (colour 0xFFEEEEEE times a brush texel times
  the alpha of texel (0,0) of Explorer's 512x384 atlas, DWM's pixel
  shader `brush(t1) * colour(t0) * mask(t2).a`), then the icons. XAML puts
  an opaque white texel at (0,0) of every atlas with a 1x1 blit, the
  first blit into the fresh target; the executor's texture BLT staged the
  source and then uploaded the dirty target through the same staging
  pair, at the target's size, so the first blit into any fresh target
  copied the target's own empty VRAM. The background drew nothing and the
  wallpaper showed through. The target's upload now comes first.
- **A window's caption was black and had no buttons** (Settings): DWM
  draws a caption from small shared atlases (32x32 for its colours,
  64x32 for each button's image) that are filled with ColorFill and with
  TexBlts from system memory, both of which the user-mode driver did on
  the CPU, and WDDM 1.1 makes no shared allocation CPU visible in a
  memory segment (the kernel driver's CreateAllocation), so the lock
  failed and the write was dropped without a word. v24 carries the
  runtime's COLORFILL (op 82) to the host for any colour render target,
  which `IDirect3DDevice9::ColorFill` runs (a non-shared target is spared
  a readback and an upload too); a TexBlt or Blt from system memory into
  a shared target goes through an upload stage, a lockable video-memory
  texture the CPU fills and the host copies (op 81). A failed lock now
  says so in the log.
- **File Explorer's header and Home page, and Notepad, drew nothing**:
  they are WinUI 3 (Windows App SDK), whose compositor made a Direct3D 11
  device on our adapter, found feature level 9_1, dropped it and tried
  again, 233 times when a window opened, then gave up. Basic Display
  (WARP, 11_1) draws them. `tools/wddm-probe.cpp` showed the 9_1 and
  that everything else it needs works (shared and keyed-mutex textures,
  Direct2D, DirectComposition, composition swap chains). What 9_2 wants
  was read out of Windows 11's own `d3d10level9.dll` with its public
  symbols (`cdb -z` on the host's copy, `srv*` path; `CapCaps`,
  `ExceedsCapsBits` over `c_aDriverVerReqLevel1Caps`, `MinCapsLevel2`,
  `MinCapsLevel3`: bit masks, minimums and per-DXGI-format support at
  D3DCAPS9 offsets; `UMAdapter::AddCapsForFormat` turns FORMATOPs into
  that support, `D3DFMT_To_DXGIFMT_10on9` picks the format): separate
  alpha blending, MaxPrimitiveCount and MaxVertexIndex of 0xFFFFF (so
  32-bit indices: v24's `D3DPT_DRAW8_INDEX32` and ranges up to 16M
  vertices, which the host draws with 32-bit indices past 65536), and
  A8, L16, V16U16 and Q16W16V16U16 as cubes and volumes. The rest of 9_2
  and all of 9_3 the core's caps already had, so the adapter now gets
  9_3 and the WinUI 3 apps draw as on Basic Display. The XP and 9x
  drivers keep their caps and 16-bit DRAW8.
- A TexBlt into a render target the host drew into reads it back first,

  keeps the host's pixels.
- d3d9.dll's LINEPATTERN, ZVISIBLE and EDGEANTIALIAS (render states 10,

Then (driver 0.3.25.0, the same day): **32-bit Direct3D on x64**, and the
flip's vertical blank.
- 64-bit Windows loads a 32-bit process's user-mode driver by
  `UserModeDriverNameWow` from SysWOW64, and the package had none: a
  32-bit Direct3D 9 program (most of the era's games) got no HAL device.
  The x86 build of the same user-mode driver (Windows 7's) is that driver
  as `d3dptumd32.dll`: everything the two drivers share (`d3dpt_wddm.h`,
  the protocol) is ULONG-wide, so the 64-bit kernel driver reads a 32-bit
  one's private data and command buffers as they are. `build-wddm.cmd`
  copies it into the x64 package, the INF's `d3dpt_Install64` installs it
  and the value, `wddm-install.ps1` signs it, and the guest-tools ISO
  carries it in `WDDM64\`. D3DGAME9 (32-bit, the reference workload) on
  build 26100, windowed: frame 300 is **pixel-identical to the native
  DXVK frame** and inside the rig golden's budget (790 pixels beyond
  tolerance 8, budget 1200), the checks the XP stage makes; D3DFEAT9 runs
  its 600 frames with no failed call. Both run as the logged-on user from
  a scheduled task (`New-ScheduledTaskPrincipal -LogonType Interactive`);
  a full-screen one needs the foreground, so it is started from the Run
  dialog (`qmp.py keys meta_l-r`), else it waits on a lost device.
- **A flip waited for nothing**: the kernel driver set the scanout's
  address when the flip's DMA buffer ran and reported its fence at once,
  so nothing ever waited for a vertical blank (full-screen D3DGAME9 ran at
  600 frames a second). A flip with a flip interval and no
  `FlipWithNoWait` now waits for the next vertical blank while dxgkrnl has
  the interrupt on: the scanout takes its address there and its fence,
  with every fence submitted after it, is reported done there, in order;
  stopping the interrupt releases it. DWM's own flips are paced so too
  (the reason step 5 opened). On Windows 11 a full-screen Direct3D 9 game
  presents through DWM (fullscreen optimizations), so it now runs at
  DWM's rate, ~33 frames a second on the PC. That rate is the guest's,
  not the host's: under that load the device's own line says `2197
  batches in 5.0 s, 1018 ms of them in the executor` (the host busy 20%
  of the time, readbacks ~2 ms each), so the next thing for speed is on
  the guest's side (DWM's and the program's CPU time, the drivers' cost
  per submission, ~440 doorbells a second). The kernel driver logs the
  first few counts of flips shown per 300 vertical blanks.
- That guest time is the kernel driver's: with a windowed D3DGAME9 the
  guest's System process took 73% of a CPU (the game 29%, DWM 10%), and
  timing the kernel driver's packets (the first few 5 s periods are
  logged: `packets in 5 s, op count microseconds`) put 2.1 s of every 5
  in paging FILLs (16 of them, ~130 ms each: every new allocation is
  cleared) and 1.0 s in the present blits (118, ~8 ms each). The guest's
  stores into VRAM are uncached under WHPX (the BAR's memory type wins
  over the guest's write-combining), so a 7 MB clear runs at ~55 MB/s.
  Register set v9 (`CAP_FILL`) has the device clear VRAM from the host
  (`FILL_ADDR` / `FILL_BYTES` / `FILL_PATTERN` / `FILL_GO`), and the
  kernel driver's FILL uses it: the fills went from ~2.1 s of every 5 to
  ~2 ms, the guest's System process from 73% to ~49% of a CPU, and the
  windowed D3DGAME9 from ~29 to 40.6 frames a second (1500 frames in
  37.0 s). Then the same register set's `CAP_COPY` (`COPY_VRAM`,
  `COPY_BYTES`, `COPY_LIST_*`, `COPY_ROWS`, the two pitches,
  `COPY_SRC_VRAM`, `COPY_GO`): the device copies between VRAM and guest
  memory named by a list of guest-physical page addresses (the kernel
  driver fills it from an MDL's PFN array or the aperture's mappings,
  64K entries allocated contiguous at StartDevice), row by row for a
  rectangle, or VRAM to VRAM. The paging TRANSFERs (1.3 s of every 5)
  and the present blits (1.2 s) now take ~2 ms and ~35 ms: the windowed
  D3DGAME9 runs **53.6 frames a second** (1500 frames in 28.0 s, from ~29
  before either), its frame 300 still pixel-identical to native DXVK.
  (`vgamem_mb=512`, a bigger segment than the default 63 MiB, had given
  only 42.6 against 40.6 before the copies moved, so no new default.)
- Edge draws its pages through Chromium's software path (`edge://gpu`:
  "Software only"; it wants a feature level 10 device a Direct3D 9-class
  driver cannot give). Acrylic: with transparency effects on, the taskbar
  is one flat colour on our adapter and on Basic Display alike (Windows'
  own choice on a low-tier adapter), so nothing of ours.
- Tried and taken out: renaming buffers (`MaximumRenamingListLength`,
  DISCARD locks with `Discard | LockEntire`) so a DISCARD lock would not
  wait behind a held flip. The memory manager renamed, but the host kept
  drawing the buffer's old place (D3DGAME9's dynamic grid vanished and its
  scene stood still), and it bought no frame rate since the game presents
  through DWM. LockCb also refuses `IgnoreSync` from a user-mode driver
  (`E_INVALIDARG`).

### The launcher's machine on a Windows host (2026-10-09)

The three things the test machine was hand-scripted for are now the
launcher's Windows 11 family on a Windows host (`bundle::Machine::
modern_args` under `cfg!(target_os = "windows")`, x64 only:
`player::cannot_start` refuses an Arm bundle there). The first version
of each was a workaround; by the end of the day each was fixed, and the
machine is Linux's: Secure Boot available, a TPM 2.0, restarts in place,
a stock install with no setup key.

- **The TPM**: QEMU refuses `CONFIG_TPM` on Windows. Patch 88 allows it
  for our in-process libtpms backend (the emulator backend now needs a
  `POSIX` host symbol; `TPMLocality.state` became a `uint32_t` for
  MSVC's enum ABI), and `build-deps.sh`'s MSVC set builds OpenSSL
  (VC-WIN64A with clang-cl and nmake, MINGW64's perl) and libtpms
  (its TPM 2.0 sources compiled by the script, with
  `patches/deps/libtpms/02-windows`: clocks, byte order, PCRE2's POSIX
  regexes, a few Windows branches). Only the MSVC QEMU (the package's)
  has it; `tpm-qtest` runs there. Under WHPX the TPM's device could not
  start at all: its command buffer and PPI region are RAM that is not
  page aligned, which WHPX tried to unmap and aborted on, as HVF did
  (patch 82); patch 89 leaves such a section alone. The workaround before it: no TPM, and
  an `autounattend.xml` with setup's `LabConfig` bypass keys on the
  drivers disc built on Windows.
- **Secure Boot without SMM**: WHPX refuses `smm=on`, and QEMU's secure
  OVMF requires SMM. `build-edk2.sh x86_64` (`build-windows.sh`'s new
  `edk2` stage) builds OvmfPkgX64 natively with Visual Studio 2022
  (EDK2's VS2022 toolchain, MINGW64's nasm, iasl from ACPICA's pinned
  source built with msbuild), QEMU's secure options but
  `SMM_REQUIRE=FALSE`: `2ksbox-x86_64-code.fd` and `-vars.fd`
  (`Arch::efi_code_file`, `efi_vars_template`). The variables are not
  protected from the guest's own kernel, which nothing here needs.
  `patches/edk2/03-ovmf-vs2022` makes it link with this Visual Studio.
  The machine is `q35` without `smm=on` and without the secure flash.
  The workaround before it: QEMU's OVMF without Secure Boot.
- **The reset**: a guest's own reset stopped QEMU under WHPX ("WHPX:
  Unexpected VP exit code 4" right after the RESET, the firmware never
  printing again), while a cold start of the same disk booted. The first
  version ran these machines with `-no-reboot` and had the player ask
  "The machine restarted" with Restart and Close, Restart exiting 75 for
  the launcher to start it again (user, 2026-10-09: "show a message to
  the user with the info and a reset button"; embed API v13). Then the
  cause: x86 WHPX never reset the partition, so the Hyper-V
  enlightenments' state (hypercall and reference TSC pages, the SynIC)
  outlived the reset. QEMU patch 87 calls `WHvResetPartition` on every
  reset, as upstream's Arm WHPX does, and Windows 11 restarted itself
  twice in one process on the test machine. The workaround went the
  same day (embed API v14), and `test.sh`'s `whpx-i386` now also
  resets SeaBIOS over QMP.

The clipboard's channel too: the MSVC QEMU had no `qemu-vdagent` (no
spice-protocol on Windows, M23 step 7), and a new Windows 11 machine,
whose clipboard is on, did not start. spice-protocol is in the MSVC set
now.

The result, on 2026-10-09: the launcher's own machine (`launcherx --new
win11` on an overlay of the test machine's disk, `--prepare`, `--play`;
`D:\vms\win11-test\launcher-test.sh` adds only the command channel)
under WHPX: `Confirm-SecureBootUEFI` False (available, off, as on
Linux), `Get-Tpm` present and ready, spec 2.0 (libtpms 1.83), a
restart in place, power-off clean and the TPM's state saved. The wizard's
family note on a Windows host is Linux's. Not yet: an install from the
launcher end to end on this PC (the test machine was installed by hand
with setup's bypass keys).
