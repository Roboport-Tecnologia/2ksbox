# Track M20: Windows 11

Proposed 2026-10-01 (user: "windows 11 insists on needing a tpm chip to
work, and I wanted our emulator to be able to run windows 11 on the mac
for people that need it for work"), opened the same day on the branch
`track/m20-win11` once ADR-024 made 2ksbox a general-purpose VM manager
("that just so happens to also be awesome at emulating vintage boxes").
Steps 1 to 3 and their open items were merged to `main` on 2026-10-01
(user), and the track continues there. Read `docs/00-status.md` first
for the track rules.

## What kind of box this is

A Windows 11 box keeps the launcher, the bundle format, snapshots, the
player window and the in-process QEMU. It uses none of the era work: no
`d3dpt-vga` (Windows 8 and later refuse XP-model display drivers), no
Voodoo 2, no x87 or SSE fast paths, no guest-tools ISO. Its display is
Microsoft's Basic Display Adapter on a plain framebuffer, with no 3D,
which is enough for office work.

## What Windows 11 checks

| Check | Where | What we give it |
|---|---|---|
| UEFI | setup, hard | EDK2 (below) |
| Secure Boot capable | setup | EDK2's secure build. Off is enough to install |
| TPM 2.0 | setup, BitLocker, Hello, some company policies | libtpms in QEMU (below) |
| 4 GB RAM, 64 GB disk, 2 cores | setup | the family's defaults |
| CPU on Microsoft's list | setup only | a current CPU model under KVM/WHPX/HVF. Under TCG, the `LabConfig` `BypassCPUCheck` key during setup |
| SSE4.2 and POPCNT | 24H2 and later, hard (the kernel uses them) | TCG has both, as does any host CPU of the last ten years |

Setup can also skip the TPM check (`BypassTPMCheck`). We don't rely on
that. The user wants this for work, and BitLocker device encryption,
Windows Hello and company compliance policies need a real TPM.

## The Mac: Windows on Arm under HVF

On Apple Silicon an x86 guest runs under TCG. Win98 and XP are fine
there because their software expects a 500 MHz machine. Windows 11
expects a current multi-core x86 and runs Defender, indexing and updates
in the background. I expect x86_64 Windows 11 under TCG on the Air to
boot in minutes and stutter at the desktop. Step 1 measures it.

UTM, Parallels and VMware Fusion all run **Windows 11 on Arm** (ARM64) as
the guest, under Hypervisor.framework at close to native speed. Microsoft
publishes the ARM64 ISO. Its own x64 emulation (Prism) runs most x64
programs, and that costs less than emulating the whole machine. For us
that means:

- A third QEMU target, `aarch64-softmmu`, built on Arm hosts
  (`scripts/configure-qemu.sh`).
- The `virt` machine with `-accel hvf -cpu max` (the host's CPU under
  HVF). Our TCG patches are i386-target code and do not apply to it.
- Devices Windows ARM64 drives in the box: AHCI for the disk and CD-ROM
  (on our own EDK2, which can boot from it), `qemu-xhci` with keyboard
  and tablet, `ramfb` for the screen, HD Audio. Networking needs
  virtio-win's ARM64 `netkvm`. Step 4's results have the rest.
- Kernel-mode drivers inside the guest (company VPN clients, endpoint
  agents) must have ARM64 builds. Prism does not run x64 drivers. Some
  companies' tools will not have them.

On Linux and Windows hosts, x86_64 Windows 11 under KVM or WHPX is the
box.

## The TPM: libtpms inside QEMU

QEMU 9.2 has the TPM devices: `tpm-crb` (q35), `tpm-tis` (ISA) and
`tpm-tis-device` (the ARM `virt` machine). What it lacks is a TPM to put
behind them. Its `emulator` backend talks over a socket to **swtpm**, a
separate process built on **libtpms** (IBM's TPM 2.0, derived from the
TCG reference code).

The plan is a backend that links libtpms into QEMU, `-tpmdev
libtpms,id=tpm0,state=<file>`, instead of shipping swtpm:

- One process, as ADR-002 wants. There is no sidecar to start, supervise
  and fit into the Flatpak sandbox.
- The backend calls `TPMLIB_Process()` for each command. Through
  `TPMLIB_RegisterCallbacks` it stores the TPM's permanent state in one
  file in the machine's bundle.
- Snapshots carry the volatile state (`TPMLIB_GetState` /
  `TPMLIB_SetState`) in the backend's vmstate. If the permanent state is
  lost, BitLocker asks for its recovery key, so cloning a machine copies
  the file and deleting one deletes it.
- It is C inside QEMU, which ADR-004 allows, the same pattern as
  `libsynth` behind `hw/audio`. Writing a TPM 2.0 in Rust is months of
  crypto and spec work, and nobody has written a complete one.
- **libtpms needs OpenSSL's libcrypto.** That is a new library for
  `scripts/build-deps.sh` (macOS, static, pinned) and for the Windows
  cross build, where the configure step disables gnutls, nettle and
  gcrypt today.

A known limit: libtpms's endorsement key has no manufacturer certificate
chain that Microsoft trusts. Anything that attests the TPM to Microsoft
will probably fail: Autopilot self-deploying mode, device health
attestation, and the Intune compliance rules built on them. Nobody has
tested this yet. Hyper-V's own vTPM has a similar problem.

## Firmware: EDK2

Yes, Windows 11 needs UEFI. QEMU's `pc-bios/` already carries EDK2 builds
from its pinned `roms/edk2`: `edk2-x86_64-secure-code.fd`,
`edk2-aarch64-code.fd`, and the variable store templates
`edk2-i386-vars.fd` (also used by x86_64) and `edk2-arm-vars.fd`. Every
package already ships `pc-bios/`. Step 1 uses them as they are.

- x86_64 with Secure Boot: `-machine q35,smm=on`, `-global
  driver=cfi.pflash01,property=secure,value=on`, the code as a read-only
  pflash, and the machine's own copy of the vars as a writable one.
- Each machine gets its own vars file in its bundle (boot order, Secure
  Boot state), copied from the template when the machine is created.
  Snapshots include it.
- QEMU's templates have no Secure Boot keys enrolled, so Secure Boot is
  available but off. That passes setup. Turning it on needs Microsoft's
  keys in the template, enrolled at build time with virt-firmware's
  `virt-fw-vars` (Python, runs under uv). Microsoft's 2011 certificates
  expire during 2026, so enroll the 2023 ones too.

## The player and the launcher

Built in step 3 ("Step 3's results" below):

- **One player binary per target, each linking its QEMU** (doc 11). The
  era's `2ksbox-player` links i386; `2ksbox-player-x86_64` is the same
  player built with `--features qemu-x86_64` into `target/qemu-x86_64`,
  and the launcher starts the one a machine needs
  (`player::player_binary_for`). The first version had one player
  opening `libqemu-embed-<target>` at run time (`dlopen`). Reverted the
  same day (user): patch 63 reserves TCG's code buffer next to the
  helpers from a constructor that must run when the image loads, before
  `main()`, and a later `dlopen` loses that on Apple Silicon (doc 22
  §5.0). The cost is a second 23 MB player in the Linux package.
- **`launcher-core`'s `Windows 11` family** (`Family::Win11`,
  `bundle::Machine::modern_args`): a q35 with SMM, EDK2's secure build,
  the libtpms TPM on CRB, the disk on AHCI, 4 GB, up to 4 vCPUs,
  `-cpu max`, `Accel::Auto`, HD Audio, the standard VGA, the tablet on
  xHCI, an e1000e with networking, the RTC in local time. The firmware
  variables (`efi_vars`, a qcow2) and the TPM state (`tpm_state`) are
  bundle files; clone copies them.
- **The form** shows what applies (no processor, Voodoo 2, MIDI port,
  floppy or boot order) and says what the family is; the Qt and mitsuami
  views hide the rows the model says do not apply (ADR-014).

4 vCPUs, 4 GB, NVMe, `-nic none`, swtpm 0.10.2 with no `swtpm_setup`
(so no endorsement key certificate, like the libtpms backend will be).

|---|---|---|

| Power-on to desktop | 29.6 s | 447.8 s (15x) |
| ACPI power-off | 9.4 s | 27.2 s |

- Setup's hardware checks passed with no `LabConfig` key: UEFI, Secure
  Boot capable, TPM 2.0 on `tpm-crb`, the host CPU. Windows reports
  26H2 build 26300.9457 Professional, `firmware=UEFI`, TPM present,

  off (QEMU's vars template has no keys).
- With no product key in the unattend file, setup stops on the key page.
  One click on "I don't have a product key" and the rest runs unattended
  (`tools/qmpc.py OUT/qmp2.sock click 399 574 1280 800`). A user installs
  by hand anyway, so the launcher needs nothing here.
- One device without a driver: `ACPI\QEMU0002`, QEMU's fw_cfg (code 28,
  harmless).
- The guest clock reads local time from the RTC, which QEMU sets to UTC.
  The family wants `-rtc base=localtime`.
- The installed disk is 16 GB.
- Our build generates neither the EDK2 files nor the VNC keymaps:
  `qemu-bundle/` links to `build/qemu/pc-bios/edk2-*.fd`, which exist
  only after `ninja -C build/qemu pc-bios/edk2-x86_64-secure-code.fd
  pc-bios/edk2-i386-vars.fd`. Step 3's build stage has to make them.
- Under TCG, once the desktop is up QEMU stays near 290 % CPU (three of
  the four vCPUs busy with Windows' startup work).

**Our TCG patches and an x64 guest.** `target/i386` is compiled into both
system emulators, so the TCG run above used the whole queue. Patches 06,
11 and 24 have long-mode branches, and the `accel/tcg` patches do not
care about the guest's mode, but no battery or benchmark has ever run a
64-bit guest. The queue was also tuned for era code (x87, SSE1/2), while
x64 Windows is SSE2 scalar math and AVX/AVX2 (`-cpu max` offers it),
which goes through helpers we never touched. A crash under TCG on an x64
guest could be one of our patches. The control is the same boot with the
switches off (patch 29's `*-fast=off`, `QEMU_TCG_OPTS`). Making x64
Windows fast under TCG would be its own optimization project, and the
TCG number above is why the Mac gets the ARM64 guest instead.

## Step 2's results (2026-10-01)

`-tpmdev libtpms,id=tpm0,state=<file>` with `-device tpm-crb`. The
backend (`tpm/qemu/tpm_libtpms.c`, patch 75) calls `TPMLIB_Process` on
QEMU's TPM worker thread. Its storage callbacks keep libtpms's "permall"
blob in the one state file, replaced atomically; a missing file is a
TPM libtpms manufactures on first start. Snapshots carry the permanent
and volatile state, and `loadvm` writes the snapshot's permanent state
back to the file, so the TPM always matches the disk it booted with.

- `tools/tpm-qtest.py` passes all 19 checks (the `tpm-qtest` host check):
  a fresh TPM, a restart on the same file, savevm / loadvm, `info tpm`.
  No guest and no firmware: qtest is the CPU.
- Windows 11 boots on it under KVM (desktop in 18.9 to 27.1 s, clean
  power-off). Its elevated `Get-Tpm` says ready and owned, and the
  endorsement key's SHA-256 is the same on libtpms and on swtpm
  (`faa2cc0c…01b5`): the backend took over swtpm's TPM, so Windows saw
  no new chip. The spike's `TPM=libtpms` does that the first time: swtpm's
  `tpm2-00.permall` is a 10-byte header and one tag-length-value record
  (tag 1, plain) around the same blob.
- QEMU allows one `-tpmdev` of any type ("Only one TPM is allowed"),
  which matches libtpms's one global TPM.
- libtpms 0.10.2 needed one deps patch on this box's glibc 2.44
  (`patches/deps/libtpms/01-strstr-const`, from libtpms's master).
  OpenSSL is 3.5.9 (LTS), static, no programs or loadable modules.
  On Linux both are hidden in QEMU's link like GLib, so a process with
  its own OpenSSL never mixes the two.
- **Windows hosts have no TPM yet.** QEMU 9.2's meson refuses
  `CONFIG_TPM` on Windows ("TPM emulation only available on POSIX
  systems"), because both upstream backends need POSIX. Ours needs
  only a thread pool, so lifting that for the libtpms backend alone is
  the Windows step, with libtpms and OpenSSL in the mingw cross build.
- The Windows 11 elevated report needs a click on UAC's Yes: Windows
  11's prompt has no Alt+Y, and focus starts on No.

## Step 3's results (2026-10-01)

- A Windows 11 bundle (an overlay of step 1's disk, fresh firmware
  variables from `launcherx --prepare`, step 2's TPM state) reached the
  desktop in 36 s on `launcherx --print-args` under KVM, and through
  `launcherx --play`, the x86_64 player, the launcher's
  control socket and the disc shelf. Both powered off from the ACPI
  button. Windows found its disk on AHCI, where it had been installed
  on NVMe, and the firmware found Windows' boot manager from empty
  variables (the fallback path on the EFI partition).
- **Why AHCI and not NVMe:** QEMU 9.2's NVMe is not migratable, and
  `savevm` refuses ("State blocked by non-migratable device"). With the
  disk on AHCI, the variables in qcow2 and the TPM's vmstate, `savevm`
  works and records the snapshot on the variables file too.
- `scripts/test.sh`: host and guest stages as before (icons,
  exec-no-device and pit-guest, the known failures); `qt-wizard` now
  opens the real Qt form on Windows 11 too.
- The Linux package ships both players and both libraries, and checks
  with `ldd` that each player resolves its own QEMU inside the package.
  The Flatpak gains the OpenSSL and libtpms tarballs and builds the
  x86_64 player and library (not built here). macOS and Windows ship no
  x86_64 player yet: the family runs on Linux only.
- **A display Windows turned off swallows the first power-button
  press**: after ten idle minutes the screen is black, the first

What it took:

- **A third QEMU target, `aarch64-softmmu`, on Arm hosts only**
  (`configure-qemu.sh`), its embed library and a third player,
  `--features qemu-aarch64` into `target/qemu-aarch64`, which `build.sh`
  signs with `packaging/macos/hypervisor.entitlements` (HVF refuses an
  unentitled process even ad-hoc signed). Two queue patches: 76 guards
  the Arm HVF code's macOS 13 calls for our macOS 12 floor; 77 keeps the
  era's ISA devices and the `hw/mesa` glue out of a target with no ISA
  bus, and `embed/` calls the gameport only under `CONFIG_GAMEPORT`.
- **`bundle::Arch`**: a Windows 11 machine's `arch` field, the host's
  own for a new machine, x86_64 for a bundle without it.
  `Machine::arm_args` writes the `virt` board; `-accel hvf` then TCG on a
  Mac when the machine is the host's own architecture (never for the
  era's i386, whose QEMU has no HVF); the required-acceleration choice is
  `hvf` there too. The wizard's acceleration note and family note know
  that a Mac's hypervisor runs only Windows 11 on Arm.
- **Our own EDK2** (`scripts/build-edk2.sh`, `build.sh`'s `edk2` stage,
  `patches/edk2/`; user decision, below). QEMU's prebuilt aarch64
  firmware stopped three things: it has **no Secure Boot**, so stock
  setup refuses ("The PC must support Secure Boot"; the TPM check
  passed); **no AHCI driver**, so it boots from neither disk nor CD on
  AHCI and the disk had to be on NVMe, which `savevm` refuses ("State
  blocked by non-migratable device"); and **ramfb's modes end at
  1024x768**, so the boot manager left the screen at 800x600, which
  Windows' Basic Display then keeps. Built from the commit QEMU's
  `roms/edk2` pins with QEMU's own options plus `SECURE_BOOT_ENABLE`
  (capable, off, no keys, as on x86_64), with the SATA/ATAPI drivers and
  ramfb modes to 1920x1080 (the board's preferred 1280x800 is now one).
  Clang and lld from Homebrew (build tools), 70 s.
- **The board**: the disk and CD-ROM on an ICH9 AHCI controller named
  `ide` (so `cdrom_args`, the disc shelf's live swap and `bus=ide.1`
  are the q35's), `tpm-tis-device`, `ramfb`, `qemu-xhci` with
  `usb-kbd` and the tablet (no PS/2 on `virt`), HD Audio, `virtio-net`
  with networking. Windows on Arm drives AHCI, the ATAPI CD, the TPM,
  HD Audio, xHCI and the HID devices in the box.

What Windows says (`tools/win11-spike.py ARCH=aarch64`, `PROBE=1`):
build 26300.9457 26H2 Pro, UEFI, Secure Boot `False` (capable, off),
`Get-Tpm` fails with 0x80284001 while `tpmtool` and WMI say the TPM is
initialised, activated, enabled, owned and ready for storage, not for
attestation (no endorsement key certificate, as on x86_64), and BitLocker
cannot bind to PCR7 without Secure Boot on. Windows on Arm also lists a
"Microsoft Pluton security processor" root device, which may be what
`Get-Tpm` trips on. No driver for QEMU's fw_cfg (as on x86_64) and the
`virt` board's 32 virtio-mmio slots (`LNRO0005`), all harmless.

### The drivers disc (2026-10-01)

`scripts/build-virtio-win.sh` (`build.sh`'s `virtio` stage, Arm hosts)
downloads virtio-win 0.1.302's ISO, pinned by sha256 (upstream publishes
none for the ISO; ours is of the file fetched 2026-10-01), and cuts
`build/virtio-win/2ksbox-drivers-arm64.iso` from it, 2.7 MB: the ARM64
Windows 11 `NetKVM` and `viogpudo` without their `.pdb` files, under
`$WinPEDriver$`, with the license and a README. The launcher puts it in
a CD drive of its own on `ide.2` of every Windows 11 on Arm machine
(`disc_library::arm_drivers_iso`; installed as `share/2ksbox/drivers/`,
which step 5's packagers must ship with `virtio-win_license.txt` among
the app's notices). A machine with no disc starts anyway, and the
launcher says what is missing.

- **Setup installs them by itself.** A stock install with the disc in
  and `virtio-net` on came up with the "Red Hat VirtIO Ethernet Adapter"
  up, 10.0.2.15, online (the desktop's weather widget loaded), and both
  drivers in the store, with no click: Windows Setup takes
  `$WinPEDriver$` from any drive. The install took 10.7 min against
  8.0 offline, and its last shutdown ran longer, which looks like
  Windows using the network it now had.
- **viogpudo** drives `virtio-gpu-pci` on the installed system ("Red
  Hat VirtIO GPU DOD controller", 1280x800), and our EDK2 draws on that
  device too (VirtioGpuDxe). But setup shows nothing on it: the screen
  stayed on the firmware's last frame for 90 s while setup ran, since
  Windows' Basic Display cannot use virtio-gpu's framebuffer and setup's
  first screens come before the drivers it loads. So the board keeps
  `ramfb`. `tools/win11-spike.py GPU=virtio-gpu-pci` runs the other.
- Live snapshots work with the read-only drivers CD attached.

## Decisions for the user

Answered: the scope (ADR-024, general-purpose; Windows 10 runs on the
same machine). The firmware source (2026-10-01, user): **our own build
for Windows 11 on Arm** (`scripts/build-edk2.sh`), since QEMU's has no
Secure Boot and no AHCI; QEMU's prebuilt secure build stays for x86_64,
which has both. Still open:

1. **Secure Boot.** Available but off (QEMU's templates, enough for
   setup), or on by default with Microsoft's keys enrolled.
2. **x86_64 Windows 11 on a Mac at all.** Step 4 made a new Windows 11
   machine the host's own architecture, so a Mac makes Windows 11 on Arm
   and the wizard offers nothing else; an x86_64 bundle copied from
   Linux still loads, emulated, with no player for it in the Mac build.
   Whether the Mac should offer x64 Windows at all is open.
